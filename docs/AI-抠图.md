# AI 抠图（r80）

## 这是什么

图标编辑器的「自动抠图」可以走两条路：

| 路线 | 依赖 | 耗时 | 何时用 |
|---|---|---|---|
| **本地算法** | 无（纯 Rust） | 5~40 ms | 默认；开关关着时 |
| **AI 模型** | 需下载模型（4.4~168 MB）+ 运行时 dll | 140~1000 ms | 用户在设置里开了开关、且模型下好了 |

**AI 是可选增强，不是替代**。开关默认关；关着时功能完全可用（本地颜色解混）。
这条设计的理由是实测出来的：本地算法在**扁平图标**上已经不错，AI 的价值在它
做不到的地方（主体与背景同色、照片类底、复杂内部）。

## 模型版本（设置 → 通用 → AI 抠图）

| 模型 | 体积 | 平均耗时 | 图标实测正确数 |
|---|---|---|---|
| **u2netp（推荐）** | **4.4 MB** | **63 ms** | **7 / 8** |
| RMBG 量化版 | 42 MB | 659 ms | 5 / 8 |
| RMBG 半精度 | 84 MB | 437 ms | 5 / 8 |
| RMBG 全精度 | 168 MB | 496 ms | 5 / 8 |

**结论出人意料**：4.4MB 的 u2netp 反而最好。原因：RMBG-1.4 为**人像/产品照片**
训练，它会把握不住的图标元素（文字、底座）当噪声删掉；u2netp 更"粗糙"，
反而倾向保留整个前景块。

所以清单里 u2netp 排第一并标"推荐"，其余三个保留给需要人像/照片效果的场景。

## 模型从哪来、为什么不入包

官方源（全部 https，下载时校验 SHA256）：

| 模型 | 来源 |
|---|---|
| u2netp / u2net | <https://github.com/danielgatis/rembg/releases> |
| RMBG 三档 | <https://huggingface.co/briaai/RMBG-1.4>（`onnx/` 目录） |

**为什么不打包进安装包**（用户明确要求）：
- 168MB 的模型会让安装包大三倍，而它**多数用户用不到**（本地算法够用）
- 模型体积差 40 倍，应该是用户的选择而不是强加

## 下载流程

```
设置里打开开关
   ↓
检查：运行时 dll 在不在（不在 → 提示"缺运行时"，下载模型也没用）
   ↓
列出 4 个版本 + 体积 + 实测速度 + 已下载标记
   ↓
点「下载」→ 卡片内出现进度条（每 1% 刷新，可取消）
   ↓
下完 → SHA256 校验 → 原子落盘（临时文件 .part + 改名）
   ↓
图标编辑器「自动抠图」自动开始用 AI；失败则静默回退本地
```

**几个必须这样做的点**（都踩过）：

- **临时文件 + 原子改名**：中途取消/断网不会留下半个损坏的模型文件
- **SHA256 校验**：代理/镜像站可能给回损坏文件，坏模型让推理直接崩
- **进度按百分比节流**：168MB 切 2600 多块，每块推一次事件纯浪费
- **取消必须清理**：`__CANCELED__` 是内部信号，不当错误报给用户

## 运行时（onnxruntime.dll）

**不随模型下载** —— 它是程序的一部分，跟 exe 放一起。

- 版本：ONNX Runtime **1.22.0** win-x64（`ort` 2.0.0-rc.10 要求 API version 22）
- 体积：11.8 MB
- 放哪：仓库的 `vendor/ort/lib/`（不入库，见该目录 README），
  `build.rs` 的 `copy_ort_runtime` 会自动拷到产物目录
- 缺了会怎样：`aimatte::runtime_available()` 返回 false → 界面提示 + 自动降级本地算法

### 为什么不用 `ort` 的 `copy-dylibs` feature

它期望 `<ORT_LIB_LOCATION>/lib` + `<ORT_LIB_LOCATION>/Release`，而官方发布包
**只有 `lib/`** —— 于是它静默什么都不拷。表现是运行时加载到系统里 Python 的
onnxruntime（实测 1.17.1），报 `The requested API version [22] is not available`。
**这个坑不报错、产物看着也正常**，所以改成显式拷贝。

### 为什么不用纯 Rust 的 tract

试过。它在两个模型上都卡在 `Resize` 算子（`FAIL: Building node Resize_42`），
ONNX 支持不完整。ONNX Runtime 是唯一实测能跑这两个模型的引擎。

## 与本地算法怎么配合

不是"二选一"，而是**互补**：

```text
  AI 的 alpha  ──┐
                 ├─→ 定 trimap ─→ 本地解混（边缘质量）─→ 输出
  本地颜色意见 ──┘
```

- **AI 说前景**（alpha ≥ 240）→ 无条件前景（AI 的语义判断这里最可信）
- **AI 说背景**（alpha ≤ 15）→ **还要本地也认为像背景**才算确定背景，
  否则交给本地连通性判
- 边缘带（中间值）→ 本地颜色解混 + 去色

第二行是关键：**第一版无条件信任 AI，实测把主体内部掏空了**
（IGN 中心被挖空、GOG 挖出白洞、Apple_Music 音符内部残留）。
本地算法按**连通性**判断背景（只有能走到图像边界的同色区域才算），
正好补上这个短板。

## 实测对比（10 个真实图标）

`docs/evidence/r80-ai-vs-local.png`（棋盘底）、`...-dark.png`（黑底看白边）、
`r80-ai-rmbg-fp16.png`（RMBG 版）

**诚实的结论：AI 与本地各有胜负，没有一边全胜。**

| 图标 | 本地算法 | u2netp | rmbg-fp16 |
|---|---|---|---|
| Excalidraw | 一般 | **好** | **好** |
| 139_邮箱 | 一般 | **好**（文字清晰） | 差（文字丢） |
| IGN | **好** | 差（中心挖空） | 差 |
| Iconify | **好** | 一般 | 一般 |
| GOG | **好** | 差（挖白洞） | **好** |
| 126_邮箱 | **好** | 好 | **好** |
| Apple_Music | **好** | 差（残留红） | **好** |
| Codeberg | **好** | 差（基本全空） | **好** |
| Lobsters | **好** | **好** | **好** |
| CNBC | **好** | **好** | **好** |

所以：
- **默认用本地算法**是对的（它更稳）
- **AI 留给它擅长的场景**：主体与背景同色、照片类底、需要"语义理解"的图
- u2netp 与 RMBG 各有强弱，这正是**清单里都保留、由用户选**的理由

## 已知限制

- AI 对**扁平图标**的"内部封闭区域"判断不可靠（会把主体内部当背景）——
  已用"本地连通性否决"缓解，但不能根除
- RMBG 系列对含**文字**的图标容易丢字（它把人像/产品当训练目标）
- 首次推理要加载模型（4.4MB ~ 0.1s；168MB ~ 0.4s），之后每个进程内复用
- 张量形状固定（u2net 320 / RMBG 1024），非正方形图会被拉伸后再缩回
