> 发布日期：2026-10-21
> 上个版本：v1.3.6
> 这一版修一个你指出的界面问题 + 两处内部健壮性（测试不再时红时绿）。

## ① 默认 / 磨砂主题下，不该出现的「刷新帧率」

你的原话：

> 「比如说液态玻璃里面有一个实时折射，然后就可以设置刷新的帧率，
>   那么在默认和磨砂的横条主题下就没有必要来设置刷新的帧率。」

### 根因：那一行只看了一个条件

「刷新帧率」这一行的显隐判定是：

```js
row.hidden = !(CONF && CONF.barGlassLive);
```

只看了**实时折射开没开**，没看**当前是哪种样式**。

而 `barGlassLive`（实时折射）是个**开销开关**，不属于外观参数 ——
切样式时刻意不让它跟着复位（玻璃预设 `GLASS_PRESETS` 的注释里写过这事）。
于是：

```text
开过玻璃样式 + 开过实时折射
     ↓
切回「默认」或「磨砂」
     ↓
barGlassLive 仍然是 true
     ↓
帧率那一行又冒出来了 ← 而这两个样式下玻璃画布根本不跑，四个按钮全是无效的
```

### 修法：两个条件同时满足才显示

```js
row.hidden = !(CONF && CONF.barGlassLive && qsBarStyle(CONF) === 'glass');
```

即：**液态玻璃样式** + **实时折射开着**，两个都满足才显示。

### 顺带补了一条漏掉的路

原来的代码只在「**开关实时折射**」时才重算那一行的显隐。而
**切样式**（默认/磨砂/玻璃三分段）这条路当时是漏的 ——
`data-style` 那轮循环只会把玻璃参数行统一设成可见，没人再去套第二个条件。

现在两条路都覆盖：

| 操作 | 帧率行 |
|---|---|
| 玻璃样式 + 实时折射开 | 显示 |
| 玻璃样式 + 实时折射关 | 隐藏 |
| **默认样式**（实时折射残留在开） | **隐藏** ← 你报的这条 |
| **磨砂样式**（实时折射残留在开） | **隐藏** |
| 从默认/磨砂切回玻璃（实时折射开） | 显示 |

### 怎么验的

真代码 + 假 DOM 跑了 8 个场景（新增 `qs_audit/glass_fps_row_run.js`），
外加静态检查 5 条（`qs_audit/glass_fps_row_check.py`）：

```
PASS  玻璃样式 + 实时折射开 → 帧率行显示
PASS  玻璃样式 + 实时折射关 → 帧率行隐藏
PASS  默认样式（live 残留 true）→ 帧率行隐藏  ← 你报的就是这条
PASS  磨砂样式（live 残留 true）→ 帧率行隐藏
PASS  从磨砂切回玻璃 → 帧率行显示
PASS  默认样式下 glass/frost 参数行收起
PASS  玻璃样式下 glass 参数行可见、frost 行收起
PASS  CONF 缺字段时不抛异常
```

抽函数体跑真逻辑而不是静态看字面 —— 否则 `qsBarStyle(CONF)` 是不是真跟着
`barGlass` / `barBlur` 变，只能靠猜。

## ② 顺带修的：两条自动化测试偶发失败

发布前一晚连着跑 300 遍测试，发现约 **1/100** 的概率红一次，
两次红在不同测试上：

```text
panicked at src\clip.rs:873      ← set_text 拿不到剪贴板
panicked at src\config.rs:2677   ← delay_ms 拿到 4321 之外的数
```

### 第一次：剪贴板（clip.rs）

`set_text` 内部的重试窗口是 300ms（`30 × 10ms`），这个数字是**产品**的取舍 ——
阻塞太久会拖累取词那条 40ms 一轮的轮询。但剪贴板是**全机器**的单例，
本机任何进程（资源管理器 / 浏览器 / Windows 自己合成格式）握它几十到几百毫秒
是常态，于是测试的前置步骤偶发失败。

**修法**：前置那几步的重试窗口加长到 ~2.5 秒（`set_text_wait` / `set_image_wait` /
`wait_image`）。2.5 秒还拿不到才失败，并把"本机有进程长期独占剪贴板"写进断言。

> ⚠ 不是"跳过"来消掉它 —— 这条测试的价值全在语义断言（图没了 / 文字回来了），
> 悄悄跳过等于把测试变成空跑。

### 第二次：测试之间互相踩（config.rs / main.rs）

这是**测试自身**的隔离缺陷：

```text
load_from / save_to / data_dir()  →  都会读 %APPDATA%
AppDataTemp::new()                →  正在改 %APPDATA%
                                   ↑ 进程级，改和读不在同一时刻
```

原来只有"正在改 APPDATA"的测试拿 `ENV_LOCK`，而**读**它的那些测试不拿 ——
并发下 A 已改完、B 正在读，照样串味。实测症状：

```text
config_survives_restart_and_corruption 断言 delay_ms == 4321
实际拿到 2 ← 那是隔壁测试 save_never_leaves_a_half_written_config
                循环里的第 3 次保存值
```

**修法**：新增一把**跨模块**的进程级大锁 `config::test_lock()`，
所有碰磁盘的测试（config.rs 自己的 17 条 + main.rs 用 AppDataTemp 的 5 条）
全部先拿它。实体放模块级而不是 `mod tests` 里，就是为了让两个文件共用同一把。

> 代价：这些测试从并行变串行，总时长 ~0.6s → ~1.5s。可接受 ——
> 换来的是"时红时绿"消失，以后测试结果才敢信。
