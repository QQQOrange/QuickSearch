> 冲突处理和安全边界情况。」

## 一、先说结论：令牌其实一直在备份里，缺的是三个地方

排查下来，`githubToken` **本来就跟着**主配置、滚动备份、云端备份走（因为备份是
`config_view()` 全量），真正缺的是三件事，而且每一件都会让用户吃亏：

| 缺口 | 后果 |
|---|---|
| 它不在任何导出分组里 | 「数据 → 导出」的勾选界面上根本看不见它，**带不走** |
| 界面上写着「留空 = 不加密」 | 留空其实走 DPAPI（加密但换机解不开），用户照着这句话理解，换机那天才发现备份作废 |
| 同步/恢复是整份覆盖 | 另一台机器没填令牌时，它那份备份里是空串，**同步一拉就把你的令牌清空** |

## 二、令牌进导出清单，且**必须加密**

`export.rs` 新增第 9 组：

```rust
Group {
    id: "secrets",
    name: "个人访问令牌",
    desc: "GitHub 个人访问令牌（PAT）。拿到它的人能以你的身份访问仓库，比 API Key 更危险",
    keys: &["githubToken"],
    private: true,
    default_checked: false,
}
```

默认不勾、标红。勾了之后落盘形态由 `write_plain` 决定：

| 情况 | 结果 |
|---|---|
| 不含令牌 | 明文 JSON，接收方直接导入（老语义不变） |
| 含令牌 + 有备份密码 | `qsEnc:1` 信封，接收方要有同一个密码 |
| 含令牌 + 没备份密码 | **拒绝导出** + 提示先设一个 |

为什么是"拒绝"而不是"退回明文"或"用 DPAPI"：明文等于把仓库访问权发出去；
DPAPI 换机照样解不开，等于给用户一个用不了的导出文件。两种都比"直接说不行"更糟。

判据用的是 `contains_secret()` —— 看**数据里有没有非空令牌**，不是看勾了哪一组。
勾了组但本机没填令牌时照旧明文，不会逼用户多输一次密码。

### 导入侧

`read_plain` 现在带 `password` 参数：遇到加密内容用**本机备份密码**解
（和「备份」页同一个钥匙，用户不用记两套）。解不开时分两种说法：

- 本机没填密码 → 「请先在「备份」页填上和导出时相同的备份密码」
- 填了但不对 → 由 `crypto` 报密码不匹配

`parse()` 那道"加密内容直接拒"的闸保留着（纵深防御：谁绕过 `read_plain`
把密文喂进来，也不会被 serde 解成一份"键全丢"的空导出）。

### 导入时令牌被换掉要说出来

一份别人给的 `.qsconf` 只要勾了 secrets 组，就能把你的令牌换成对方的 ——
之后你所有 GitHub 请求都走他的账号，他能看到你查了哪些仓库。
不阻止（用户可能就是想换），但 `import_items` 会比较前后值，变了就加一句
「个人访问令牌已被文件里的值替换」。

## 三、界面不再让你猜「能不能换机恢复」

### 改掉的错话

```diff
- 设了密码，所有备份都是 AES-256-GCM + Argon2id 加密的；密码丢了就解不开。留空 = 不加密。
+ 所有备份都会加密。区别只在用哪把钥匙 —— 这决定了它能不能换台电脑恢复：
+   · 设了备份密码：任何一台电脑填上同一个密码就能恢复；密码丢了就解不开，也没有后门。
+   · 没设：用 Windows 账户加密。数据不会明文落盘，但只有这台电脑、这个 Windows
+     用户能解开，换机器恢复不了。
```

### 新增状态条

后端新命令 `backup_security_state()`：

```json
{ "hasPassword": false, "envelope": "dpapi", "portable": false,
  "hasToken": true, "secretCount": 3 }
```

界面按 `portable` 渲染：

- **✓ 可跨设备恢复** —— 换电脑：填同一个密码 → 从云端恢复，凭据一起回来
- **⚠ 仅本机可解** —— 换电脑后解不开；想跨设备就补个密码再备份一次

后面跟一句现状：「当前配置里有 3 项凭据会跟着备份走 · 含 GitHub 个人访问令牌」。
**只报"含令牌"，不显示令牌本身** —— 这条状态条不需要、也不该出现凭据。

`secretCount` 来自 `config::secret_count()`：只数填了值的项（纯空白不算），
百度那套「老字段 + 新 map」只算一次（否则 1 个 Key 报成 2 项，用户反而怀疑漏了）。

备份密码输入框一改，状态条 400ms 后自动重算（等 `set_setting` 落盘）。

## 四、同步/恢复不再清空令牌

真实场景：

> A 机填了令牌，B 机没填。B 改了图标、备份上云 → A 机启动同步，按「云端较新」
> 整份拉下来 —— B 那份里 `github_token` 是空串，A 的令牌就没了。之后 A 所有
> GitHub 请求变成匿名（每小时 60 次），用户完全不知道原因。

两条路分别堵：

| 备份格式 | 做法 |
|---|---|
| View（云端 / 手动导出 / 老备份） | 靠 `apply_view` 既有的「空值不覆盖」；额外记下"确实发生了保留"以便提示 |
| Config（`save_to` 的滚动备份） | 整份赋值，以前**一个字都没防**；现在显式调 `keep_local_secret` |

保护的是"被清空"，不是"被更新"：备份里真有令牌时照常恢复进来（换机不用重填）。

`restore_from_text` 现在返回一句补充说明，由调用方拼进 toast：

```
；本机的个人访问令牌已保留（备份里没有，没被清掉）
；个人访问令牌已随备份恢复
；个人访问令牌为空（备份里没有），需要的话请重新填
```

两边都没有凭据时返回空串 —— toast 不为一句话加废话。

## 五、换机恢复失败时给出可执行的下一步

以前只有一句「DPAPI 解密失败」，用户不知道是文件坏了还是自己操作错了。
新增 `unseal_hint()`，按原因分三种：

| 情况 | 提示 |
|---|---|
| DPAPI 信封解不开 | 这份是做它的那台电脑加密的（当时没设备份密码），只能在原机解开；以后先设密码再备份 |
| 密码信封 + 本机没填密码 | 去「备份」页把当时那个密码填上 |
| 密码信封 + 密码不对 | 密码不匹配，改成当时那个 |

原文案（`crypto::decrypt_dpapi` 的"换过 Windows 用户/机器"）仍留在括号里，
给需要看底层原因的人。
