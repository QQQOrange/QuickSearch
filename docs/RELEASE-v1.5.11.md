# v1.5.11 —— 修「能检测到新版、却下载不下来」

> 用户报：「虽然能够检测到新的版本，但是却不能够顺利的下载。」

查下来**不是网络问题**（虽然现象很像），是三个自己的毛病叠在一起。每个都有实测证据。

---

## 根因一：下载被 15 秒的**总超时**掐断

`agent()` 上挂了 `.timeout(15s)`。在 ureq 里这个超时管的是**整个调用**：
DNS + 连接 + TLS 握手 + **把响应体读完**，全算在里面。

那个 15 秒本来是给「查一下有没有新版」用的 —— 那种请求几百毫秒就回。但同一份
配置被下载复用了：13 MB 的更新包要在 15 秒内下完。本机实测 3 MB/s 尚可勉强，
**300 KB/s 就要 45 秒，必然被掐断**。

更糟的是它断在 `read()` 上，报出来是「下载中断」，看着跟网络被重置一模一样。
所以谁都会先去查网络，而网络是好的。

**修**：下载改用独立的 [`download_agent`]，只限制两件事 ——
建连接（8 秒）和两次读之间的空等（60 秒）。只要还在往下走，下多久都行。

---

## 根因二：断了就从 0 重来，没有续传也没有重试

旧代码是「`remove_file` → 一次性流式读完」。任何一次 TCP 中断就整个失败，
而且下一次点「下载并安装」**还是从 0 开始**。在不稳的网络里就是永远下不完。

**修**：
- 按断点续传（`Range: bytes=N-`），断了从那个位置接着下；
- 一次下载里自动重试 3 轮，失败退避 700 / 1400 ms；
- 失败分两类，断点留不留不同对待：
  - **传输层中断**（连接断、读超时）→ **保留断点**，下一轮接着下；
  - **内容层不对**（HTTP 4xx、SHA256 对不上）→ **丢掉断点**，下轮从头来
    （否则会越拼越错）。

校验改成**从落盘文件重算 SHA256**，而不是复用下载过程中的增量 hash ——
续传时前面那段字节不在本次流里，增量 hash 必然对不上。

---

## 根因三：只有一条下载链路，而那条恰恰是最不稳的

更新包有两个入口，最后都 302 到同一个 CDN，但**入口域名不同**：

| 入口 | 本机实测 |
|---|---|
| `github.com/.../releases/download/...`（`browser_download_url`） | ❌ **直连超时** |
| `api.github.com/repos/.../releases/assets/{id}`（带 `Accept: application/octet-stream`） | ✅ 正常 |

这个差异解释了一切：**检测更新**走的是 `api.github.com`（通），所以能发现新版；
**下载**走的是 `github.com`（不通），所以下不下来。同一个软件，两条路一个通一个不通。

> 顺带说明：`curl` 能下是因为它走了系统代理（响应头里有 `HTTP/1.1 200
> Connection Established`），而 ureq **不走系统代理**。所以"我命令行下得好好的"
> 和"软件下不下来"可以同时成立。

**修**：主源失败自动换备源。从 API 响应里取 `assets[].id` 拼出备用地址。
（`QS_GITHUB_ASSET_API` 是给探针用的逃生口，正式启动不走它。）

---

## 根因四（顺带）：失败原因一闪就没

前端原来在下载失败时：

```js
hint.textContent = '更新失败';          // 页面上只有这四个字
toast('更新失败：' + msg);               // 真正的原因在这里，1~2 秒后消失
```

用户只来得及看见"失败了"，不知道断在网络、校验还是被拒，也就没法判断该重试
还是换条路。

**修**：
- 具体原因**留在页面上**（包括「已自动重试 3 轮」）；
- 主按钮**自动变成「用浏览器下载」**，下面的直链一并显示 ——
  与其让用户反复点同一个按钮，不如直接给他另一条路。

## 验证

### 真实下载（对 github.com 与 api.github.com 各跑一次）

```text
只给主源： Connection timed out（已自动重试 4 轮）—— 73.14 秒后失败
主源 + 备源：已下 13415936 / 13415936 → 落地 13,415,936 字节 → 10.83 秒成功
```

第二条就是修好之后的行为：主源 8 秒超时 → 自动换备源 → 下完。

### 断流续传（本地假服务，精确控制断点）

`update::tests::下载断了能续上而不是从头再来`：
服务器**第一次只发 40% 就关连接**，客户端必须保留断点、第二次带 `Range` 续上。

```text
PASS  下载断了能续上而不是从头再来
PASS  断点已完整时不用重下
PASS  下载源主备顺序
PASS  传输失败留断点内容失败丢断点
PASS  备源地址与逃生口
```

另外两条 `#[ignore]` 的真实网络测试（`真实下载一次`、`真实续传从半个文件接着下`），
发版前手动跑：`cargo test 真实下载 -- --ignored --nocapture`。
