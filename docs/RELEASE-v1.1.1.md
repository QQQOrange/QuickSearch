# Quick Search v1.1.1

修 v1.1.0 里被用户实际用出来的问题，并**重做下载链路**。

**推荐所有 v1.1.0 用户升级** —— 旧版的 AI 抠图下载几乎无法完成
（实测 606 秒仍未下完），升级后同样的下载 **9 秒完成**。

**程序本体 12.07MB**（不含任何 AI 模型），单 exe、免安装。

---

## 这一版最重要的：下载从「几乎下不动」变成「几秒钟」

### 实测对比（同一个探针，改前 vs 改后）

| | 改之前 | 改之后 |
|---|---|---|
| 运行库 | 下 **69MB 的 zip** 再解压 | **直接下 11.84MB 的 dll** |
| 实测耗时 | **606 秒仍未下完**（0.11 MB/s） | **5.7 秒下完** |
| 模型 | u2netp 走 ~1 MB/s 的源 | **1.5 秒下完** |
| 端到端 | 失败，留下 68.5MB 的 `.zip.part` | **9.1 秒全好，无残留** |

### 为什么之前那么慢

逐源实测（直连，各 10~40 秒，不带任何代理）：

| 源 | 速度 |
|---|---|
| GitHub 直连 | **0 MB/s**（20+ 秒收不到数据） |
| hf-mirror（u2netp 原来唯一的源） | 0.14 MB/s |
| 官方 zip 走 gh-proxy | 10.63 MB/s |
| **modelscope（RMBG）** | **11.63 ~ 27.06 MB/s** |

两个真问题：

1. **为了 11.84MB 的 dll 去下 69MB 的 zip** —— 白下 57MB，还多一个"解压"失败点
2. **u2netp（默认模型）只有一个 ~0.14 MB/s 的源**

### 怎么改的

1. **运行库直接下 dll**：11.84MB 一次纯拷贝，不解压、无中间文件。下完比大小
   （12,418,080 字节），下成错误页或下了一半都会被拒。
2. **模型与 dll 传进本项目的 release**（5 个资产，约 316MB），
   走 gh-proxy 加速；同时按实测把更快的源排到前面：
   - RMBG 三个 → **modelscope 第一**（11~27 MB/s），自己 release 第二
   - u2netp → **自己 release 第一**（1.39 MB/s，比 hf-mirror 快 10 倍）
3. **允许并行下载**（见下）

## 并行下载：运行库和各模型可以同时下

**用户原话**：「要允许同时下载，运行库跟每一个模型都可以同时下载，也都要单独下」。

改成两层：

| 对象 | 并发策略 | 为什么 |
|---|---|---|
| **模型** | **完全并行** | 各用各的 `.part`（文件名带模型 id），不冲突 |
| **运行库** | **只下一次**，其它线程等 | 它是同一个文件，并发会重复下 11.84MB |

等的一方界面显示「等运行库下载完成…」，不会让进度条卡在 0% 像死机。

### 运行库有了**独立下载按钮**

设置 → 通用 → AI 抠图 →「缺少推理运行时」那一行右边有「下载运行库」，
不必非得点某个模型才触发。

## 修了什么

### 1. 点一次「下载」，却像重复下载了好几遍（重要）

**用户原话**：「我在设置通用 ai 抠图里面点击下载引擎，它会下完之后再进一步的
重复下载，这是一个 bug」。

**真因不在前端，而在后端没有防并发。** 用户机器上的日志把现场完整记了下来：

```text
134368000379  ai_matting_download: 开始 rmbg-full
134368000384  ai_matting_download: 开始 rmbg-fp16
134368000389  ai_matting_download: 开始 rmbg-quantized
134368000395  ai_matting_download: 开始 u2netp          ← 4 个下载在 16ms 内同时开始
134368000910  运行库失败：gh-proxy.com: 解压失败 不是有效的 zip（找不到 EOCD）
              ghfast.top:   解压失败 不是有效的 zip（找不到 EOCD）
              github.com:   解压失败 不是有效的 zip（找不到 EOCD）
134368001737  开始 rmbg-full / rmbg-fp16 / rmbg-quantized / u2netp   ← 又来一轮
```

每个下载都会先取运行库，而运行库那个 69MB 的 zip 用的是**固定文件名**。
于是并发时：

- 线程 A 刚建好 zip，线程 B 把它删了 → A 随后 `read` 报 `os error 2`
- 线程 C 写到一半，线程 D 去读 → 「找不到 EOCD」（读到不完整的文件）
- **谁都没成功** → 界面看起来就是"下完了又下一遍"，而且每轮都失败

**残留物证**：用户机器上捡到一个 `onnxruntime.zip`，
`71,529,644` 字节 —— 完整文件是 `72,368,545` 字节，**少了 0.8MB、找不到 EOCD**。
这正是"被另一个线程打断"的典型形态。

**修法（两层）**：

1. **下载锁**：同一时刻只允许一个下载。重复点会明确提示
   「已经有一个下载在进行中，请等它结束（或点「取消」）再试」，
   而不是两个一起跑、互相破坏。
   > ⚠ 锁的位置很关键：必须在**发起下载的那一刻**拿到，并覆盖
   > **运行库 + 模型两段**。我第一版把锁放在 `download()` 里，结果盖不住
   > 它前面的"下运行库"那一段 —— 两个线程照样并发抢那个 zip。
   > 探针 `r80j` 的 1a/1b 就是专门抓这个的。
2. **临时文件名唯一化**：带进程 id + 纳秒时间戳，不再共用固定名。
   这是第二层保险 —— 万一将来放开并行，也不会再互相踩。

### 2. 版本号没更新

**用户原话**：「桌面版本的版本号没有更新」。

**真因**：版本号有**三处**是手写的，而发版时只改了其中一部分 ——
`src/config.rs` 里的 `pub const VERSION = "1.0.0"` 被漏掉了，而它正是喂给界面的那一个。

**修法**：改成编译期从构建配置读取

```rust
pub const VERSION: &str = env!("CARGO_PKG_VERSION");   // 不可能写错
```

顺带清掉另外三处同类隐患：

- `package-lock.json` 里的版本
- 关于页 HTML 里写死的初值 `v1.0.0`（现在放占位符 —— 宁可显示"—"，
  也不显示一个**错的**版本号）
- 界面取不到版本时的回退默认值

还改了「更新日志」的一个设计毛病：原来最新那条写的是
`ver: 'v' + 当前版本 + ' · 最新'` —— 版本号是动态的，于是不管发到哪个版本，
它都显示"当前版本"，而里面的文字却还是旧版功能。**用户看到的就是"版本号没更新"
（其实更新了，但日志内容没跟着走）**。现在每条都写死自己的版本号。

### 3. 旧位置的模型残留

**用户原话**：「原来已经把模型都下了一遍，现在在软件里面已经把模型位置做了修改，
那么原来的版本的好像还在一开始下载的位置，需要你做进一步的清除」。

v1.1.0 把模型默认位置改成了 `<程序目录>/抠图模型`，但**旧位置的文件没人管**。

**修法**：新增「清理残留」（设置 → 通用 → AI 抠图），**每次启动也会自动清一次**。

清什么（只清"确定是垃圾"的）：

| 类型 | 说明 |
|---|---|
| `*.zip` / `*.zip.part` | 下运行库的中间产物（实测用户机器上留了 68MB 一个） |
| `*.onnx.part` | 模型下到一半中断的临时文件 |
| 旧位置的 `*.onnx` | v1.1.0 改默认位置之前下到数据目录的，现在用不上了 |
| 空的旧 `models/` 目录 | 清空后连目录一起删（**非空则留着**，不碰你自己的东西） |

**当前模型目录里的 `.onnx` 一个都不碰** —— 那是你的模型，删了要重下 168MB。

### 4. 顺手修的一个小问题

`download()` 里建目录用的是**旧路径**，而文件写在**新路径** —— 两者在 v1.1.0
改默认位置之后分叉了，于是每下完一个模型都会在数据目录里**凭空多出一个空的
`models` 文件夹**。现在目录一律从落盘路径推导，不可能再分叉。

## 安装

1. 下载 `QuickSearch.exe`（**直接覆盖旧版即可**，配置与模型都不受影响）
2. 双击运行（无需安装）
3. 升级后**首次启动会自动清一次残留**，把旧版本留下的临时文件与旧位置的模型清掉
4. 想用 AI 抠图 → 设置 → 通用 → AI 抠图 → 打开开关 → 点「下载」
   （会自动连运行库一起下好，**不用重启**）

**系统要求**：Windows 10/11 x64，WebView2 Runtime（Win11 内置；Win10 若缺失会提示）。
